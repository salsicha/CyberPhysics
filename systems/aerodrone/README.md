# Aerodrone

This is the canonical definition of the repository one quadrotor. The physical deployment is `compositions/aerodrone_hardware.yaml`; Gazebo, Genesis, and Isaac compositions model this same vehicle and mount this directory for the same controller and interface configuration.

- `config/arducopter.params` is the hardware baseline Navigator/ArduCopter configuration: the first file to load on the aircraft (then `config/arducopter_gps_input.params`). It keeps pre-arm checks and the RC/GCS failsafes enabled.
- `config/arducopter_sitl.params` holds the SITL-only relaxations (no arming checks, failsafes or auto-disarm, because the simulators have no RC transmitter or GCS). `applications/ardupilot_sitl/scripts/run_arducopter_sitl.sh` layers baseline, SITL relaxations, the GPS-denied corrections file, then backend physics compensation (`applications/{genesis,isaac}/config/aerodrone_sitl.params`). Never load the SITL file on hardware.
- `config/arducopter_gps_input.params` configures the GPS-denied corrections, which are on by default in every Aerodrone stack (`GPS_INPUT_CORRECTIONS=true` in `config/topics.env`; `GPS_INPUT_CORRECTIONS=false` turns them off): DemNav/WildNav corrections reach ArduPilot as GPS 2 via MAVLink GPS_INPUT from `applications/aerostack2/scripts/ardupilot_navigation_bridge.py`. SITL loads the file automatically; on the aircraft it must be loaded by hand (see [GPS-denied corrections on the aircraft](#gps-denied-corrections-on-the-aircraft)). See `tools/gps_denied_sitl_test.md` for what it does and its measured limits, and `tools/gps_denied_sim_test.md` for GPS-denied runs of the Gazebo, Genesis and Isaac stacks.
- `CAMERA_MOUNT_YAW_DEG` in `config/topics.env` must match the physical OAK-1 mount (heading of the image top relative to the nose, counter-clockwise from above; 0 = image top toward the nose). The value 0.0 is a nominal assumption for a forward-aligned nadir mount (camera looking straight down, image top toward the nose); confirm it on the built aircraft by flying over a known landmark, or by checking a still image, before relying on DemNav/WildNav fixes. The OAK-1 is body-fixed: DemNav and WildNav locate the point below the vehicle from the MAVROS attitude at each image stamp, so a tilted mount (not modelled) shifts every fix by the height above ground times the mount tilt, and `attitude_sigma_deg` (1 deg by default) should cover the mount and EKF attitude errors.
- `config/topics.env` defines the stable Aerodrone and simulated sensor topic contract consumed by the navigation stack. `applications/aerostack2/scripts/validate_aerodrone_navsim.py` (the `validation` profile of the simulation compositions, see `applications/aerostack2/README.md`) reads the same variables to check that a simulation provides them; `tools/gps_denied_sim_test.sh` runs it with the compositions' `denial` profile, which disables GPS 1 for a window of simulation time during the cruise and scores the flight against ground truth.
- `config/tracking.env` holds the object tracker's limits (15-120 m above ground, 5 m/s), follow-mode defaults and tuning (`tracking.md` is the interface contract; `applications/aerostack2/README.md`, "Object tracker"). `compositions/aerodrone_tracking.yaml` repeats them as the aircraft's values; `docker compose -f compositions/aerodrone_hardware.yaml --profile tracking up` adds the tracker, which geolocates on the DemNav DEM cache (seed it for the flying area before flight) and also relies on `CAMERA_MOUNT_YAW_DEG`.
- `config/sensors.yaml` records the physical sensor equivalents, topics, and nominal operating limits. Serial-number-specific camera intrinsics and measured mounting extrinsics should be added here when calibration is performed on the built aircraft.

Simulation terrain, missions, models, scripts, and acceptance tests are not physical-system configuration and intentionally do not live in this folder.

## GPS-denied corrections on the aircraft

The navigation bridge only forwards corrections once the flight controller reports every value in `config/arducopter_gps_input.params` (EKF3 source set 2 = GPS position only with barometer height and compass yaw, `EK3_SRC_OPTIONS=0`, GPS 1 kept primary, and `GPS2_TYPE` 0, or 14 left by a previous run). It reads them through MAVROS and never writes EKF source parameters to the autopilot; it only toggles `GPS2_TYPE` between 0 and 14 at runtime. Until they match it logs `GPS_INPUT corrections NOT active ...` with each wrong parameter, sends nothing, and the fusion node keeps applying its own offsets. It keeps checking, so loading the file arms forwarding without restarting the stack. Parameters changed after the check passed are not re-checked: restart the `navigation_bridge` container after changing them.

Load the parameters once on the Navigator (ArduCopter 4.6; validated in SITL on 4.6.3):

1. Load `config/arducopter.params`, then `config/arducopter_gps_input.params`, with a tool that reads `NAME,VALUE` files:
   - MAVProxy, from a computer that receives the vehicle's MAVLink (for example BlueOS's ground-station endpoint on UDP 14550, with QGroundControl closed): `mavproxy.py --master=udpin:0.0.0.0:14550`, then `param load systems/aerodrone/config/arducopter.params` and `param load systems/aerodrone/config/arducopter_gps_input.params`.
   - Mission Planner: Config, Full Parameter List, Load from file, then Write Params, once per file.
   - QGroundControl cannot read `NAME,VALUE` files: set the values in `arducopter_gps_input.params` one by one in Vehicle Setup, Parameters.
2. Reboot the flight controller (MAVProxy `reboot`, or Reboot Vehicle in QGroundControl).
3. Read the values back (MAVProxy `param show EK3_SRC*`, `param show GPS*`), start `compositions/aerodrone_hardware.yaml`, and check that `docker logs navigation_bridge` shows `GPS_INPUT corrections ACTIVE: flight controller parameters verified` and `ros2 topic echo /navigation/autopilot_corrections_active` shows `data: true`.

GPS-denied flight has only been tested in SITL (the lite test and the Gazebo, Genesis and Isaac stacks: `tools/gps_denied_sitl_test.md`, `tools/gps_denied_sim_test.md`), whose IMU is far better than the Navigator's. Before relying on it, fly a supervised test: safety pilot with RC override ready to take over in AltHold, line of sight, open area, `CAMERA_MOUNT_YAW_DEG` confirmed and DemNav/WildNav caches seeded for the site. Check that arming shows no `GPS 2` pre-arm error, that the bridge logs `Sent N GPS_INPUT corrections` while flying on GPS, then deny GPS 1 at altitude in GUIDED with an RC switch set to the GPS Disable auxiliary function (`RCx_OPTION=65`), starting with about 30 s. The bridge must log `GPS2_TYPE=14` and `EKF source set 2`, and the aircraft must hold position; corrections more than about 7 s apart make the EKF failsafe land it. Re-enable GPS, confirm `EKF source set 1` after 10 s, land, and confirm `GPS2_TYPE=0` after disarming. Lengthen the denied interval only after reviewing the logs.
